# DUTchMate Agent Tooling Guide

This guide holds the detailed usage rules for Spec Kit, Graphify, and the selected Superpowers skills. It is subordinate to `AGENTS.md`, which says when each tool applies (`AGENTS.md` §9.3). The governing order for product and implementation decisions is defined in `AGENTS.md` §2.

## Reproducible Tool Versions

The shared Spec Kit scaffold and its ten `speckit-*` Codex skills are
version-controlled. Graphify and the selected Superpowers skills are local
installations excluded by the root `.gitignore`; generated Graphify output is
also excluded.

### Spec Kit

DUTchMate's managed scaffold was generated by GitHub Spec Kit **1.0.12** using
the Codex integration and shell scripts. Install the matching CLI release with:

```bash
uv tool install specify-cli \
  --from git+https://github.com/github/spec-kit.git@v1.0.12
specify version
specify integration status
```

The committed `.specify/integrations/*.manifest.json` files contain the
managed-file hashes. Do not commit `.specify/feature.json` or per-machine
`extensions/*/local-config.yml` overrides.

### Graphify

Use Graphify **0.9.48** as a local tool and regenerate its ignored
project-local Codex integration on each workstation:

```bash
uv tool install graphifyy==0.9.48
graphify install --project --platform codex
graphify --version
```

The generated `.codex/skills/graphify/` tree and `.codex/hooks.json` remain
local because the hook records the workstation's executable path.

### Superpowers

DUTchMate pins reproduction of the selected local skills to the immutable
upstream release **obra/superpowers v6.4.1**. Existing untracked snapshots are
not authoritative; recreate the ignored project-local subset from that exact
tag rather than copying an unversioned installation:

```bash
git clone --depth 1 --branch v6.4.1 \
  https://github.com/obra/superpowers.git ../dutchmate-superpowers-v6.4.1
cp -R ../dutchmate-superpowers-v6.4.1/skills/brainstorming \
  ../dutchmate-superpowers-v6.4.1/skills/systematic-debugging \
  ../dutchmate-superpowers-v6.4.1/skills/test-driven-development \
  ../dutchmate-superpowers-v6.4.1/skills/verification-before-completion \
  .agents/skills/
```

Only those four skills are part of the DUTchMate workflow. Their local copies
are not redistribution inputs and must remain untracked.

## 1. Selective Spec Kit Usage

GitHub Spec Kit is an optional specification-to-implementation workflow for substantial features.

It is **not** the default workflow for routine DUTchMate development.

Use Spec Kit when a change is large enough that a focused implementation specification, implementation plan, and task breakdown materially reduce ambiguity or coordination risk.

Good candidates include:

- a new subsystem;
- a new hardware/software protocol;
- continuous-acquisition or evidence-model foundations;
- ownership/release/reacquire behavior;
- reconnect/lifecycle behavior spanning multiple components;
- persistence/schema design;
- evidence retention and retrieval;
- the normalized backend contract;
- a major cross-cutting backend capability;
- a feature spanning several architectural layers.

Do not use Spec Kit by default for:

- localized implementation changes;
- straightforward bug fixes with a known cause;
- dead-code removal;
- mechanical refactors;
- formatting/configuration/documentation-only work;
- already-small tasks that are fully specified.

### Governing Authority

Spec Kit does not replace or redefine `docs/project_context_core.md`. The governing order is defined in `AGENTS.md` §2.

When Spec Kit is used, its generated artifacts must remain subordinate to `docs/project_context_core.md`.

Do not ask Spec Kit to rediscover or rewrite product semantics already defined there.

Use the relevant portions of `docs/project_context_core.md` as constraints and create only the focused implementation detail needed for the current feature.

### Preferred Lean Workflow

Prefer the smallest Spec Kit workflow that is sufficient.

For most substantial DUTchMate features, prefer:

```text
specify
→ plan
→ tasks
→ implement
```

Use additional Spec Kit stages such as clarification, checklists, analysis, or convergence only when they provide concrete value for the feature.

Do not run every available Spec Kit stage automatically.

### Avoid Duplicate Sources of Truth

Do not create competing specifications, plans, or status documents.

Before generating a Spec Kit artifact:

- check whether the behavior is already defined in an existing focused specification;
- reference existing normative documents instead of duplicating them;
- avoid restating large sections of `docs/project_context_core.md`;
- keep generated feature artifacts narrowly scoped.

`docs/development_status.md` remains the authority for current project progress and next step.

Spec Kit feature plans/tasks are implementation aids, not project-wide status records.

### Token and Context Discipline

Keep Spec Kit usage token-conscious:

- scope each feature narrowly;
- reference only relevant governing sections;
- avoid regenerating unchanged requirements;
- do not repeatedly re-run planning stages without a concrete reason;
- implement one coherent task group at a time when a feature is large;
- remove or archive superseded temporary planning artifacts when they no longer provide value.

Use the coding agent directly for small work rather than invoking Spec Kit merely for process consistency.

## 2. Graphify Usage

Graphify is for architectural navigation and impact analysis, not routine code browsing.

Use Graphify for:
- architecture/subsystem exploration;
- cross-module impact analysis;
- shared interfaces/ports;
- significant multi-module refactoring;
- architectural-layer tracing;
- unfamiliar subsystems;
- boundary violations.

Do not use it by default for:
- localized changes;
- isolated test failures;
- known symbols/literal searches;
- a single well-understood module;
- dead-code removal after consumers are known;
- documentation/config/formatting-only changes.

Prefer source inspection and `rg` for straightforward navigation.

When Graphify is appropriate:

1. prefer one focused `graphify query`, `graphify path`, or `graphify explain`;
2. keep the query narrow;
3. use a modest budget;
4. verify important relationships in source/tests;
5. stop querying once the impact area is understood.

Do not read `graphify-out/graph.json` directly.

Read `graphify-out/GRAPH_REPORT.md` only for broad architecture review or when targeted queries are insufficient.

Run:

```bash
graphify update .
```

only after meaningful structural changes such as module moves/additions/removals, shared interface changes, dependency-direction changes, or significant multi-module refactors.

Run it once near completion, not repeatedly.

## 3. Selective Superpowers Skill Usage

Only the four skills below are part of the normal DUTchMate Superpowers toolset. They are invoked selectively rather than as a mandatory end-to-end workflow. `verification-before-completion` is required before declaring a development slice complete where Superpowers is available. Where it is not, the validation requirements in `AGENTS.md` §8 still apply.

### systematic-debugging

Use for unclear reproducible failures, races/timing failures, inconsistent reconnect/UART/USB/persistence/lifecycle behavior, or fixes that do not explain root cause.

Do not use for obvious localized corrections.

### test-driven-development

Use when regression risk matters, especially for state machines, concurrency/ownership, reconnect, protocol parsing, persistence invariants, and externally visible behavior.

Do not manufacture failing tests for mechanical cleanup or clearly dead code.

### verification-before-completion

Use before declaring a development slice complete.

Completion claims require fresh validation evidence.

Run focused tests during implementation and the complete required validation gate near completion.

### brainstorming

Use only when a genuine design choice remains open: a new subsystem, materially different architectures, a new protocol/hardware-software boundary, or multiple viable requirement interpretations.

Do not use it for already-specified implementation, migration, cleanup, or routine bug fixes.

Do not enable or invoke the full Superpowers workflow by default. Use only the four skills above according to their stated triggers; `verification-before-completion` is required before declaring a development slice complete where Superpowers is available.
